# INOVATX Project Roadmap to First Client Go-Live

Target go-live: 2026-12-01
Current date used for planning: 2026-10-13

This roadmap is built directly from the PRD and the UML model in this directory. It is intentionally phase-gated, milestone-based, and strictly scoped to the objective of being ready for first clients by 2026-12-01.

## 1. Project North Star

Primary objective:
- Launch a working multi-tenant EdTech LMS + CRM + AI coaching platform for the first client cohort by 2026-12-01.

Success criteria:
- Django Core is operational with tenant-aware RBAC and RLS.
- Moodle SSO and provisioning work for at least one institutional and one individual onboarding path.
- AI Socratic coaching works end-to-end with fair-use controls.
- Payment flow and license activation are testable and traceable.
- Security, RBAC, tenant isolation, and data integrity are proven via automated checks.
- The system is stable enough to support a small pilot launch without production-level overengineering.

## 2. Scope Boundaries and Execution Guardrails

### 2.1 Hard Scope Rules
- Only tasks in the current phase are active.
- No work on Phase II features while the current phase is not closed.
- No speculative architecture, cleanup, or broad refactors outside the active milestone.
- No “nice-to-have” features unless they are explicitly required by the current milestone’s acceptance criteria.
- No work on SME/NGO expansion, advanced CRM modules, or broader ecosystem products until after first client go-live is complete.

### 2.2 Task Discipline Rules
- Every task must map to one or more PRD requirements or UML diagrams.
- Every task must have an owner, acceptance criteria, and completion evidence.
- Every task must produce a tangible deliverable or decision artifact.
- Any code generated by AI must be tagged to:
  - the exact requirement ID it satisfies,
  - the corresponding architecture component,
  - the specific phase and task it belongs to.

### 2.3 AI Grounding Guardrails
These are mandatory rules for all AI-generated code and implementation support:

1. Requirement-first rule
   - AI output must be traceable to a requirement in the PRD or a UML model element.
   - If a request cannot be traced to a requirement, it is out of scope.

2. Phase-lock rule
   - AI may only implement items belonging to the current active phase and task.
   - No references to future phases or future features are allowed in code comments, planning, or designs.

3. One-issue-per-task rule
   - Do not bundle multiple disconnected features in a single code generation pass.
   - Each generation must correspond to one task with one crisp acceptance criterion.

4. No speculative abstractions rule
   - Do not design generalized frameworks, broad service layers, or reusable models unless the current task requires them.
   - Prefer the minimal implementation that satisfies the current requirement.

5. Evidence-before-merge rule
   - Every implementation must include verification evidence: passing tests, lint/build steps, or explicit validation output.
   - If evidence is missing, the task is not complete.

6. Security-first rule
   - No public exposure of FastAPI without explicit approval.
   - No bypass of tenant isolation, RBAC, or webhook validation.
   - Secrets are never embedded in code or generated artifacts.

7. No scope creep rule
   - If a task drifts into non-related work, stop and reframe the task before proceeding.

8. Decision log rule
   - Any design decision not explicitly in the PRD must be recorded in a Phase Decision Log with rationale and impact.

9. Minimal output rule
   - Keep AI output narrow and exact. Do not generate long, unrelated boilerplate or tutorial content.

10. Exit-criteria gate rule
   - A phase is complete only when every task in that phase has passed verification and the phase exit criteria have been recorded.

## 7. What Not to Do

These are explicitly out of scope until go-live is complete:
- SME/NGO CRM expansion
- general-purpose enterprise project management modules
- broad CRM redesign
- non-essential AI features beyond the Socratic tutoring requirement
- multi-region deployment work
- major refactors unrelated to the active phase
- any feature not mapped to PRD requirement IDs and the UML architecture boundaries

## 8. Phase Gate Template

Every phase should close with this format:

- Phase name and dates
- Milestones completed
- Tasks completed with evidence
- Remaining risks
- Outstanding unknowns
- Scope confirmed or corrected
- Go / no-go decision for next phase

## 9. Critical Recommendation

Do not parallelize broad workstreams. Keep the team on one active phase at a time and strictly enforce the phase gate. The first client release is a controlled product delivery event, not a broad platform expansion. The project remains on-task only if every artifact, code change, and decision directly advances the current phase’s deliverable and the final 2026-12-01 launch objective.
